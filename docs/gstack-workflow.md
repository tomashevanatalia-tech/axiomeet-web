# Цикл проверенного результата

Проектная адаптация принципов gstack; upstream runtime не установлен и не требуется.
Источник: https://github.com/garrytan/gstack. Это описание процесса, а не команда установки.

## Масштаб и полномочия

Явное поручение пользователя определяет границы. Анализ, план, review и QA сами
по себе не разрешают правки, публикацию, отправки, merge или production-операции.
Для реализации выполняй согласованный объём; не расширяй его ради роли или этапа.
Простой обратимый запрос проходит короткий путь: результат → действие → проверка.
Не создавай spec, интервью и совещание ролей для опечатки или малого docs-изменения.

## Минимальный полный цикл

1. **Результат и критерии.** Для кого и зачем задача, наблюдаемое «готово»,
   границы и способ проверки. Совет или черновик может быть конечным результатом.
2. **Факты и альтернативы.** Прочитай действующие инструкции и затронутые
   материалы, найди существующее решение. Раздели факты и предположения;
   сравни минимальный вариант с расширением существующего, когда выбор существенен.
3. **Риски и план.** Назови файлы, зависимости, права, проверки и откат по риску.
   Сохрани безопасные проектные ограничения, обязательное review, CI и порядок PR.
   Спрашивай только о пробеле, меняющем результат или разрешение.
4. **Исполнение.** Выполни разрешённые шаги, сохраняя чужие изменения и принятые
   решения. Обнаруженный отказ не обходи другим инструментом или исполнителем.
   Недоступный обязательный шаг обозначь блокером; независимую часть продолжай.
5. **Проверка.** Сверь конкретный diff и версию с критериями, включая негативный
   сценарий. Проверки выбирай по изменению и текущим правилам проекта.
   Красный или недоступный обязательный гейт не считай пройденным, даже если
   сбой известен или считается flaky; зафиксируй причину и дальнейший шаг.
6. **Приёмка и улучшение.** Покажи результат, доказательства и честный остаток.
   Для существенных изменений используй независимого проверяющего, если доступен;
   повторная самооценка и несколько ролей одной сессии не являются независимым review.
   Пользовательскую приёмку не объявляй состоявшейся без подтверждения.
   После повторяемого сбоя предложи одно улучшение; для мелочи ретроспектива не нужна.

## Доставка и данные

- Публикуй только в разрешённом объёме. При поручении подготовить draft PR
  остановись на проверенном draft PR: не снимай draft, не включай auto-merge,
  не добавляй метки автоматического выпуска, не сливай и не деплой.
- Существующие проектные команды применяй только внутри разрешённого режима.
  Явные ограничения задачи имеют приоритет над их шаблонным commit/push/ship.
- Не устанавливай gstack runtime, автообновления, не импортируй browser cookies;
  не передавай код, переписку и персональные данные внешним review-сервисам.
- Не читай и не публикуй секреты. Тестовые записи выполняй только в разрешённой
  изолированной среде; доступ к production не разрешает тестовые мутации.
- Различай authored, tested (какие проверки и версия), merged, deployed
  (какая среда), accepted (какие критерии). У каждого статуса своё доказательство.
  Созданный PR и зелёный CI не доказывают выкладку или пользовательскую приёмку.

## Контрольные сценарии

| Запрос | Ожидаемое применение |
| --- | --- |
| «Только проанализируй проблему» | Факты, альтернативы, риски и вывод; без правок и публикации |
| «Исправь опечатку» | Узкая правка и проверка текста; без полного spec и расширения задачи |
| «Подготовь draft PR для существенного изменения» | Критерии, план, применимые тесты и независимое review; без merge/deploy; красный гейт явно остаётся блокером |
