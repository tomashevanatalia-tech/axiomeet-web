# axiomeet-web — правила разработки

Канон для всех моделей — этот файл. Владелец репозитория меняет правила через
PR; существующие CODEOWNERS и обязательное ревью сохраняются. Личные настройки
и шаблоны других проектов не заменяют правила проекта. Поручение пользователя
задаёт результат и разрешённую стадию; инструмент не расширяет полномочия.

## Цикл результата

1. Найти существующий код и задачу; записать границы, критерии и способ проверки
   в той же задаче/PR. При продолжении сверить ветку, PR и незавершённый результат.
2. Выбрать план и инструменты по риску. Малая правка: поиск → правка → проверка.
   Дополнительные роли необязательны; подробности читать только по теме.
3. Изолировать чужие изменения веткой/worktree, коммитить только свои пути.
4. Выполнить применимые lint/типы/тесты/сборку из конфигурации. Баг подтвердить
   тестом «красный до → зелёный после»; UI — живым сценарием и адаптивностью.
5. Проверить diff: замечание требует сценария и доказательства. Отсеять ложные
   срабатывания, исправить подтверждённые дефекты. Самопроверка не заменяет
   обязательное независимое ревью.
6. В пределах поручения довести PR через действующие проверки и порядок merge.
   Внедрение доказать в целевой среде; анализ/draft завершить на заказанной стадии.
   Написано, проверено, слито, выложено и принято человеком — разные состояния.

## Ограничения и опыт

- Секреты, .env и сырые личные данные не читать/публиковать ради контекста;
  конфигурацию получать через действующее подключение, не выгружать окружение.
- Сохранять действующие права, admin и публичные маршруты внутри их области;
  административный доступ не отменяет изоляцию организаций.
- Схема БД — версионными миграциями, без runtime DDL; выпуск последовательно,
  с проверкой совместимости и отката. Нет БД — пункт не применим.
- Обязательные CI, approvals, release gates и очередь сохраняются. Skipped,
  cancelled, flaky и отсутствие проверки не считать успешным прогоном.
- Новые расходы, расписания, отправки и тестовые записи в prod требуют действующего
  поручения. Уже разрешённые действия не требуют повторного подтверждения.
- Команды и подключение моделей/LightRAG проверять по факту. Отсутствие сервиса
  не блокирует поиск по доступному коду и не разрешает обход доступа.
- Зависимость другого репо связать с его PR и версией в исходной задаче, без
  второго бэклога. Урок писать в существующие документы: причина → правило → проверка.
  Новый обязательный механизм обосновать реальной проблемой и проверить его проводку.
- Реальный блокер: выполненное, точное недостающее условие и ближайший шаг.
